## 3. Крок 2 — Antipattern Discovery
| № | Проблема | Де проявляється | Чому це проблема |
|---|---|---|---|
| 1 | God Function | build_analytics_report(), початкові рядки 16–65 | фільтрація, обчислення і формування звіту в одній функції |
| 2 | Mixed Responsibilities | цикл обробки замовлень | логіку обчислень важко тестувати незалежно від побудови звіту |
| 3 | Magic Numbers | 0.0 та 100.0 | призначення чисел неочевидне |
| 4 | Magic String | статус cancelled | бізнес-значення не винесене в іменовану константу |
| 5 | Неявний контракт вхідних даних | order.get() і float(...) | некоректні значення можуть спричинити винятки; правила валідації не визначені |

Дублювання calculate_growth не зараховано як підтверджений дефект: у фактичному файлі є лише одне визначення, хоча коментар говорить про копіювання.

## 7. Крок 6 — Lessons Learned
**Кількість ітерацій:** п'ять логічних ітерацій, згрупованих у два коміти.
**Найважча ітерація:** декомпозиція build_analytics_report(), оскільки треба було розділити обчислення та формування звіту, не змінюючи його структуру й поведінку для скасованих замовлень.
**Регресія:** у контрольному локальному запуску доданих тестів регресій не виявлено.
**Lesson learned #1:** виділення функцій за відповідальністю робить код зрозумілішим і дозволяє тестувати компоненти незалежно.
**Lesson learned #2:** перед видаленням дублювання або зміною API треба перевірити фактичний код і використання функцій.
**Що змінив би наступного разу:** до початку роботи встановив би pylint і radon, зафіксував автоматичні baseline-метрики та додав characterization-тести.
**Критерій Done:** основні критерії виконано: декомпозицію завершено, API збережено, тести пройшли, Pylint оцінив код на 10.00/10, усі блоки Radon мають клас A. Baseline-метрики до змін відсутні, тому числове порівняння метрик «до/після» неможливе; фактичне дублювання також не знайдено.

## 9. Контрольні запитання
**1. Чим реінженерія відрізняється від рефакторингу?** Рефакторинг локально покращує структуру без зміни поведінки; реінженерія системно реструктурує модуль зі збереженням зовнішнього інтерфейсу.
**2. Коли доцільна реінженерія?** Коли є системні проблеми: висока складність, God Function/Class, дублювання, тестовий борг або змішані відповідальності.
**3. Що таке Cyclomatic Complexity?** Кількість незалежних шляхів виконання функції; зі зростанням метрики збільшується кількість сценаріїв для тестування.
**4. Що таке God Function?** Функція, яка виконує надто багато різних завдань і порушує принцип єдиної відповідальності.
**5. Для чого Reengineering Plan?** Він визначає цільову структуру, послідовність змін, критерії завершення та спосіб перевірки до модифікації коду.
**6. Що таке Extract Function?** Винесення логічного блоку в окрему функцію з чіткою відповідальністю.
**7. Для чого regression tests?** Щоб перевірити, що наявна функціональність не зламалася після змін.
**8. Що таке Test Coverage?** Частка коду, виконана під час тестування; високий coverage сам по собі не гарантує відсутності помилок.
**9. Чому важливо зберігати зовнішній інтерфейс?** Щоб інші модулі могли працювати без змін у своєму коді.
**10. Як виконати відкат?** Застосувати git revert до відповідних комітів, не переписуючи історію спільної гілки.
